# BIR Form Workflow

## Find the references

- Identify the form and revision in the source package named by the user. From the repository root, the local extraction starts at `../_extracted_embedded_files/forms/`, with assets in its sibling `img/` directory. Use the matching revision for field IDs, numbering, eligibility, choices, calculations, and validation. If the source is unavailable, report which mappings or rules could not be confirmed.
- For changed fields, verify the section, item number, control type, column meaning, and profile ownership against the source. Read the column headings before interpreting a field ID suffix. Adjacent fields can represent taxpayer and spouse, separate entries, or different amounts such as income and withholding.
- Before editor changes, read [TaxMate design decisions](../../../DESIGN.md) and the relevant rows in the [implementation guide](../../../docs/verification/taxmate-implementation-guide.md#audited-ux-decisions). Pick a production screen for each changed interaction. Match the user’s task, data ownership, and when the edit takes effect. Trace the route through its shared components, styles, state owner, and tests. Use [June 2013 Form 1701](../../../docs/verification/1701-baseline.md) for complex editor patterns.
- When the source, guide, code, or tests disagree, trace the conflicting rule through the affected callers and run the same synthetic values through the relevant paths. Record the exact references, user impact, and which source should change. Apply the target revision’s verified rules and the applicable audited UX decision. Surface unresolved conflicts before changing a filing rule, workflow, or architecture.
- For print, follow the HTA’s active Print Preview handler through to the artwork and value placement. June 2013 Form 1700 uses `printme()` → `printOCR()` to overlay values on four images. Use the matching HTA output for the BIR form and the rendered 1601EQ PDF for the app’s report bands, including its source-reference and print-date footer. Start at `src/lib/printing/return-report.ts` for the bands.
- Use `src/lib/forms/printing/form-1601-eq-print.svelte` as the app print precedent.

## Apply the change

- Reuse the matching domain component first, then the public TaxMate UI adapters and shared theme and layout styles. Match controls to field meaning. Use labeled checkboxes for independent choices, radio groups for visible exclusive choices, searchable pickers for long code lists such as PSOC, and numeric or currency controls for counts or money. Keep computed values as plain read-only text aligned with editable amounts.
- Follow the production flow for inline entry. Use `Sheet` for a self-contained child edit with a local draft, validation, Add or Update, and Cancel. Use `Dialog` for a focused choice or confirmation and `Page` for a full return. Keep the return’s **Save draft** persistence boundary and preserve focus on return from an overlay or when navigating to a linked field.
- Keep navigation and save orchestration in the editor route, form mapping, calculations, and validation in the existing form modules, and persistence in the workspace and its typed desktop clients. When a rule affects multiple outputs, trace it through the existing form runtime and reuse the rule at its current owner.
- Show profile-managed taxpayer and spouse details from the saved profile with the existing edit-profile action. Group TIN segments in one control where users enter them. Preserve segment positions, leading zeros, incomplete drafts, and saved filing choices.
- Preserve source sections and item numbers. Keep fields for the same item on one row at desktop widths, with one description and consistent amount columns. Use column headers for taxpayer and spouse and retain each person’s column when only the other person has an applicable amount. Match widths to expected values, use one divider per boundary, and place pagination below the form. Apply the form’s schedule and payment-detail rules.
- Review each affected toggle in both directions. Apply the verified rule for retaining or clearing dependent values. For example, keep an inactive amended-return amount in the working draft and exclude it from applicable calculations and outputs. Clear an over-remittance disposition when the balance no longer qualifies. Preserve unrelated entries.

## Verify and show the result

- Run `bun run check`, the relevant unit tests, and the [local browser checks for affected workflows](../../../docs/verification/taxmate-implementation-guide.md#verify-locally). Run `bun run test:run` when changing shared layout, field mapping, defaults, or calculations. Reproduce a reported regression with an existing check or a focused assertion before changing the implementation when feasible, then rerun the same check after the fix. Start with `tests/browser/individual-income.spec.ts` for general income-return flows.
- Run `bun run verify:1701` for June 2013 Form 1701 changes and shared editor changes that affect it. Confirm the 320px and 390px joint-filer wrapping checks both run and pass across all 17 pages with conditional sections enabled. Short references fit within two lines, the item and filer each stay intact, and labels stay within their container without clipping or overlap. The document fits the viewport, and a sampled link on each page with references opens and focuses its target.
- For behavior changes, enter synthetic values through the normal editor and verify affected subtotals and totals through save, reopen, validation, and export where applicable. Exercise affected filing states and tax regimes, including single, joint with matching rates, and joint with mixed rates where supported. Check blank versus zero, avoid extra clicks for a sole applicable choice, and use a sparse older draft when merging fields.
- For layout changes, capture every affected editor page at desktop and narrow widths after overlays settle. Include populated schedules, long values, and blank and populated optional controls. Verify amount alignment, bounded inputs, single dividers, readable labels, keyboard order, overflow, and pagination. For review, supply these previews, the exercised filing states, and the affected rendered PDF pages. Resolve findings against that evidence before sign-off.
- For print changes, inspect each affected PDF page for page count and orientation, values in their boxes, clear borders, and one expected header and footer per page. Verify the native export path when changing desktop integration and state any gaps.
- Reuse the verification run to generate previews for the affected editor and PDF surfaces. In the handoff, show those previews and cite the production reference, shared components or rules reused, intentional departures, checks run, and any verification gaps.
